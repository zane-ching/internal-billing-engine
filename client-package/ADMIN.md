# Distributing this package — read before sending it to anyone

Audience: whoever owns the billing rollout. `INSTRUCTIONS.md` is the developer-facing
file; this one is for you.

## The short version

```bash
# 1. Receiver must be up, on HTTPS, with RECEIVER_AUTH_TOKEN set and enforced.
#    (repo root: docker compose up -d --build; logs must show auth=ENABLED)

# 2. Build the zip with the endpoint and token baked in.
cd client-package
python3 build.py --endpoint https://otel-billing.internal.cyclotron.com --token <TOKEN>

# 3. Note the sha256 it prints. Publish it next to the download.

# 4. Send ../client-package.zip through an ACCESS-CONTROLLED channel only.
#    It contains a live token — treat the file itself as a credential.
```

Recipients unzip and double-click `Install`. Nothing else is required of them —
no terminal, no token to paste. Read the rest of this file before step 4; the
baked-in token is a real tradeoff, not a free convenience.

## What's in the package

| File | Purpose |
|---|---|
| `INSTRUCTIONS.md` | Developer-facing setup, what's collected, uninstall |
| `Install.command` / `Install.bat` | **The one-click launchers.** Double-clicked; take no arguments |
| `Uninstall.command` / `Uninstall.bat` | Same, for removal |
| `Verify.command` / `Verify.bat` | Same, for re-checking a machine |
| `install.sh` | macOS shim — finds `python3`, hands off to `configure.py` |
| `install.ps1` | Windows shim — finds a real `python.exe`, hands off to `configure.py` |
| `configure.py` | The actual install/uninstall/verify logic, shared by both platforms |
| `claude-repo-tag.py` | The repo-tag hook that gets installed |
| `VERSION` | Package version — bump when you change anything here (currently `1.1.0`) |
| `build.py` | Builds the zip. **Not shipped inside it** |
| `.gitattributes` | Pins LF on `.sh`/`.py`/`.command`, CRLF on `.ps1`/`.bat`. **Not shipped inside it** |
| `billing-config.json` | Endpoint + token, generated by `build.py` **into the zip only** |

The `.gitattributes` line-ending pins are load-bearing, not tidiness: a Windows
checkout with `autocrlf` would otherwise hand macOS a CRLF `install.sh`, and bash
fails on the carriage returns with `$'\r': command not found` before the installer
does anything at all.

The settings merge lives in `configure.py` only, so the two platforms cannot drift
apart. The launchers are wrappers around the shims, which are wrappers around
`configure.py` — if you add a platform, write another shim; don't reimplement the
merge.

## Building the package

```bash
python3 build.py --endpoint https://receiver.internal:4318 --token <TOKEN>
```

That writes `../client-package.zip` with `billing-config.json` inside it, which is
what lets the launchers run with no arguments. The token is generated straight
into the archive and never written into the source tree, so it stays out of git.

To build the older flavour, where the developer must supply both values:

```bash
python3 build.py --no-config
```

The double-click launchers will fail on a `--no-config` zip — that build is for
people driving `install.sh` / `install.ps1` with explicit flags.

`build.py` refuses to build if a *source* file contains an API key or a 64-char
hex token, so a stray paste cannot leak into a release. Bump `VERSION` when you
change anything.

## Sending it out — the zip is now a credential

**Read this before you distribute a one-click build.** Baking the token in is what
removes the terminal step for developers, and it is a real tradeoff:

1. **The zip contains a live shared token.** Anyone who obtains the file can write
   arbitrary rows into billing truth, and the package is unsigned, so nobody
   downstream can tell whether it was modified in transit. Distribute it through a
   channel with access control — a 1Password item, or an internal share restricted
   to the rollout group. **Not** email, not a Slack channel, not a link that
   forwards. If it leaks, rotate `RECEIVER_AUTH_TOKEN` on the receiver and rebuild;
   the old token keeps working until the receiver stops accepting it.
2. **Publish the sha256** that `build.py` prints, next to the download. It is the
   only integrity check a recipient has. Note that a baked token is part of the
   archive, so each token gets its own checksum — publish the one for the exact
   file you sent.
3. **Give people an `https://` endpoint.** `build.py` and `configure.py` both
   refuse a plaintext `http://` URL unless `--allow-insecure` is passed, because
   every export carries a developer's work email, repo names and cost — plus the
   shared token — in cleartext.
4. **Tell people what it collects before they install it**, not after. The
   installer now prints the collection notice and waits for a keystroke before it
   writes anything, but that is a backstop, not the announcement. The
   developer-facing list is in `INSTRUCTIONS.md`.
5. **Expect the OS security prompts.** A `.command` from a downloaded zip is
   quarantined by Gatekeeper ("unidentified developer"), and a `.bat` trips
   SmartScreen. Both are one-time and documented in `INSTRUCTIONS.md` — put the
   workaround in your rollout message too, or you will field the same question
   repeatedly. Signing the package would remove both; nothing here is signed.

## Verifying a machine

The installer self-verifies, and anyone can re-check later by double-clicking
`Verify.command` / `Verify.bat`. From a shell, the endpoint is optional on a
packaged build and required otherwise:

```bash
bash install.sh verify                                   # macOS, packaged endpoint
bash install.sh verify --endpoint https://receiver…      # macOS, explicit
.\install.ps1 -Verify                                    # Windows, packaged endpoint
.\install.ps1 -Verify -Endpoint https://receiver…        # Windows, explicit
```

Verify prefers the token actually installed in `~/.claude/settings.json` over the
packaged one, so it reports on the machine's real configuration rather than on
what the zip wishes were true.

Verification POSTs an empty body to `/v1/ping`. The receiver checks auth before
routing the path and acknowledges unknown paths without storing anything
(`billing/otel/receiver.py:243`, `:280`), so this proves reachability and auth
while writing **nothing** into `otel.db`.

One caveat worth knowing: a receiver running **without** `RECEIVER_AUTH_TOKEN`
accepts any token, so a green verify against an open receiver does not prove the
token is correct. Enforce auth on the receiver (`--require-auth`) before you rely
on that signal.

## Blockers to clear before a company-wide push

These are from this repo's own `README.md`, and they are still true in the code.
The package is ready; the pipeline behind it is not.

1. **The receiver handles requests serially.** `receiver.py:290` uses `HTTPServer`,
   not `ThreadingHTTPServer`, and `otel_store.py:146` opens a single
   `sqlite3.connect(path)` with no WAL. One slow or oversized POST blocks every
   other machine's export. README Phase 3.2 is explicit that fixing the server
   without also fixing the store **throws at runtime** — do both or neither.
2. **`receiver.log` never rotates.** `receiver.py:_log()` appends every request
   forever. On a fleet that fills the disk, and a full disk stops ingest.
3. **No backups.** `otel.db` is the sole source of billing truth. README Phase 3.4
   wants a nightly `sqlite3 .backup` (not a file copy of a live DB) with a *tested*
   restore.
4. **No TLS on the pilot endpoint.** README Phase 1.4 wants the Caddy sidecar in
   `docker-compose.yml` enabled and DNS pointed at the VM. Until then every export
   carries a work email, repo names, cost — and the shared token — in cleartext.
5. **Auth enforced, not just configured.** The receiver accepts *anything* while
   `RECEIVER_AUTH_TOKEN` is unset; it warns at startup, but a warning in a log is
   not a control. Set the token, confirm `auth=ENABLED`, then restart with
   `--require-auth`. Until you do, a green `Verify` on a developer's machine proves
   reachability but **not** that their token is correct — an open receiver accepts
   any token.
6. **Employee notice.** README Phase 0.3: the pipeline stores `user_email` per repo
   per day. That is per-developer monitoring; HR/legal notice or works-council
   consultation may be required depending on jurisdiction. "Cheap now, expensive
   after rollout."
7. **Coverage numbers from the pilot.** README Phase 2: *"Do not start the fleet
   rollout until coverage is a number worth defending to a client."* Run
   `python -m billing.reconcile --start … --end …` and look at the
   truth → captured → tagged funnel before widening.

Roll out in waves (10% → 50% → 100%), watching receiver load and the `unknown`
rate at each step.

## Known gaps in this package

- **Linux has no shim.** Only macOS and Windows were requested. `configure.py` is
  platform-neutral and works on Linux; it just needs an `install.sh` equivalent
  (or reuse `install.sh` — it is plain bash and should work unmodified).
- **This is the opt-in track only.** The MDM/enforced path is
  `deploy/managed-settings.json` plus `deploy/claude-wrapper.sh`, and per README
  Phase 4.3 those two must ship *together* — settings without the wrapper looks
  like success while being entirely unbillable.
- **The hook records the interpreter path found at install time.** If a developer
  later removes or relocates that Python, the hook stops firing silently. Re-running
  the installer fixes it. A wrapper script indirection would be more robust.
- **No signing or integrity check.** Anyone who can modify the zip in transit can
  change the endpoint or the hook, and now also read the token out of it. Publish
  the checksum, and treat the archive as a secret in its own right. Signing would
  also remove the Gatekeeper/SmartScreen prompts developers hit on first run.

- **Token rotation means re-distributing the package.** Because the token now
  lives in the zip, rotating it invalidates every copy in circulation: rebuild,
  re-send, and have people double-click Install again (re-running is idempotent).
  With the older `--no-config` flavour only the 1Password entry changed. If you
  expect frequent rotation, that tradeoff may not be worth the saved terminal step.

- **A developer can read the token.** They could already — it is written into
  `~/.claude/settings.json` on every installed machine — but shipping it in the
  zip means it is readable before install, by anyone the file reaches, whether or
  not they ever install.

## Fixed relative to `pilot-package/`

- **One click instead of a command line.** Developers double-click a file; they
  never open a terminal, paste a URL, or handle a token. The endpoint and token
  ride along in `billing-config.json` — see the tradeoff above, it is not free.

- **Merges instead of refusing.** The old `install.sh` bailed out when
  `~/.claude/settings.json` already existed and told the developer to hand-merge
  JSON. Most developers have that file, so at company scale that is a support
  ticket per developer.
- **Windows works at all.** The old package was bash-only. It also relied on
  `chmod +x` and the shebang, which do nothing on Windows, and on invoking a bare
  `.py` path, which needs a file association that a `--scope user` Python install
  does not create. The hook command now names the interpreter explicitly.
- **Dropped `OTEL_LOGS_EXPORTER=none`.** `pilot-package/settings.json` set it;
  `deploy/README.md` warns that Claude Code's logs exporter only accepts `otlp`
  and `console`, so `none` is unrecognised and makes it **error on startup and
  exit**. The key is now omitted, and `configure.py` deletes it from machines that
  ran the pilot.
- **Idempotent, backed up, and reversible.** Re-running replaces its own entries
  instead of stacking duplicates; a timestamped backup is written before any
  change; `uninstall` removes exactly the keys and hook entries it owns and leaves
  everything else alone.
- **Atomic writes.** Settings are written to a temp file and `os.replace`d, so an
  interrupted install cannot leave a truncated `settings.json` — which would break
  Claude Code on that machine.
- **Self-verifying.** The installer tells the developer immediately if the token is
  rejected or the receiver is unreachable, instead of failing silently and
  producing no billing data.
